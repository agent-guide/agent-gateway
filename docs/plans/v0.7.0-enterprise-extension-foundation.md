## Configuration principle under review

The durable target is recorded in
[Enterprise Extension Contract, section 11.3.1](../design/enterprise-extension-contract.md#1131-target-principle-host-independent-extension-configuration).
Caddyfile manages Caddy host configuration; internal extensions use ConfigStore
and are managed through Admin API or Bundle apply in both server modes. This
section is pending review, not evidence of implemented behavior.

After document confirmation, the implementation scope is:

1. Remove static extension inputs from Caddyfile/Caddy JSON, standalone static
   Bundles and distribution/runtime bootstrap options. Reject the removed input
   paths explicitly; do not silently ignore configuration or import it into the
   database on startup/reload. Preserve linked registration and manifest assembly.
2. Make Manager startup load extensions only from ConfigStore. Remove static
   extension ownership and conflict handling while retaining mutation safety,
   dependency ordering, leases, state fencing and sanitized events.
3. Keep dynamic Bundle validation/apply/export and Admin CRUD as the configuration
   workflow. A static Bundle containing extensions must fail before activation;
   an empty extensions section does not configure a module. Do not change static
   ownership for providers, routes or other resource families in this work.
4. Update Community and paired consumer fixtures, contracts, examples, package
   documentation, root/nested AGENTS, guides, references, architecture and release
   notes to describe the landed behavior. Inventory the candidate public signature
   changes and update both consumers without retaining legacy static aliases.
5. Verify API/Bundle round trips, startup from persisted envelopes in both modes,
   rejection of static inputs, preparation/persistence failure isolation and
   lifecycle regressions. Rerun full Community and paired exact-commit candidate
   gates on the new implementation; historical candidate evidence does not prove
   the ConfigStore-only behavior.

Current architecture, guides and references continue to describe checked-in
behavior until that implementation lands.

## Remaining release work, after the configuration decision is resolved

1. Select the exact clean release commit; both repository-owned Community gates
   and remote CI must pass for that source. Publish the Community `v0.7.0` tag.
2. Run `make test-extension-consumer-release` after publication. Its fresh caches,
   pinned published dependency and `GOWORK=off` must succeed without replacements.
3. In the paired repository, resolve the published tag into `go.mod`/`go.sum`,
   run `scripts/verify-community release` from fresh caches and record actual
   tag/commit, command, toolchain and result in its compatibility manifest.
4. Verify paired release CI for that dependency, then declare only the designated
   package/symbol/tag surfaces protected. No repository-wide Enterprise-ready claim.
5. Delete both foundation plans and remove their index entries after permanent
   documents and manifests describe the accepted release.

The remote has no `v0.7.0` tag as checked on 2026-10-10. Local tags and candidate
replacements cannot satisfy published dependency acceptance. Neither a hosted
release nor a remote CI result is inferred from local checks. Commercial module,
license, SBOM and customer delivery gates remain independently owned.
