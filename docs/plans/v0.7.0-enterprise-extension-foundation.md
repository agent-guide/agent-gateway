# v0.7.0 Enterprise Extension Foundation Plan

## 0. Plan Contract

This plan delivers the Community-side public foundation required by separately
maintained distributions and modules. It targets `v0.7.0` and replaces the
previous Guardrails delivery target. Guardrails remains a Proposed design and
continues on its own feature branch; it is not committed v0.7 scope.

The planning baseline is the final `v0.6.1` tree. Before implementation, every
package name and extraction point must be re-audited against that tree. Code is
the source of truth for current behavior, durable decisions belong in
`docs/design/enterprise-extension-contract.md`, and this plan must be corrected
when either changes.

The release objective is:

> make Community a safe, reusable foundation for separately compiled
> distributions by publishing reusable binary entry points, explicit linked
> capability manifests, bounded extension configuration and Admin composition,
> stable cross-cutting context/event contracts, and one real protected SPI that
> proves the model end to end.

This is not a generic plugin platform. Every runtime SPI remains domain-owned,
and Community remains independently useful without any external module.

## 1. Committed v0.7.0 Outcomes

The release delivers:

- reusable public construction/run entry points for the Caddy gateway,
  standalone daemon, and management CLI;
- a code-owned manifest of capabilities and modules linked into each binary;
- a stable module identity and configuration-registration contract used at
  startup and local validation, never for runtime code discovery;
- a narrow Admin route-contributor contract under the existing protected Admin
  mount;
- a public, bounded request attribution context with optional subject, tenant,
  route, Agent, run, VirtualKey, trace, span, and parent correlation plus
  allowlisted namespaced attributes, without implementing enterprise IAM;
- a deliberately stable public event envelope and sink boundary that does not
  expose `internal/observability/usage`;
- a protected `LimiterBackend` SPI, with the existing in-process limiter adapted
  as the Community reference implementation;
- reusable external-consumer contract suites;
- an independently built consumer fixture proving that an external module can
  be assembled without importing Community `internal/` packages or copying a
  command, dispatcher, gateway, or protocol implementation;
- precise package- and tag-level Enterprise-ready declarations rather than a
  repository-wide compatibility promise.

The paired private repository owns its binaries, proprietary modules,
entitlement integration, release packaging, and customer delivery. During
development it may use an uncommitted sibling `go.work`, and a non-release
compatibility build may pin the exact candidate Community commit. Release-gated
CI and release builds must consume the released Community tag.

## 2. Explicit Non-Goals

v0.7.0 does not implement:

- Community Guardrails, DLP, AI Firewall, Memory, Request Pipelines, RAG, or
  durable Workflows;
- OIDC, SAML, SCIM, LDAP, enterprise tenant storage, RBAC, ABAC, or OPA/CEL;
- a production Redis, PostgreSQL, Kafka, KMS, Vault, or SIEM connector;
- a universal `Plugin` interface, runtime-downloaded code, Go `plugin.so`, or a
  general service locator exposing `AgentGateway`;
- protected versions of every candidate SPI such as `PolicyEvaluator`,
  `IdentityResolver`, `SecretResolver`, `CheckFactory`, `Retriever`, or
  `ConfigStore` creator;
- a license SDK, entitlement product, commercial module ID, private schema, or
  customer-specific behavior in Community;
- a second configuration store, Admin server, event pipeline, or protocol
  dispatcher for external modules;
- compatibility guarantees for exported Community APIs that are not explicitly
  designated and contract-tested as protected surfaces.

The v0.7 context and event contracts are cross-cutting transport contracts, not
implementations of enterprise identity, policy, metering, or compliance.

## 3. Work Package F0 — Contract Freeze And Current-Code Audit

Before extracting public packages:

- audit `cmd/agw`, `cmd/agwd`, `cmd/agwctl`, `caddy/gateway`,
  `standalone/server`, Gateway Bundle validation, `pkg/admin`, the VirtualKey
  limiter, and the observability pipeline;
- enumerate every public constructor that currently exposes an `internal/`
  type and define the smallest public wrapper or adapter needed by an external
  distribution;
- define stable module IDs, capability IDs, schema versions, duplicate and
  unknown-module errors, and manifest ordering;
- define secret-reference identification before generic Gateway Bundle
  environment expansion, plus validate/apply/export semantics that retain the
  reference token and never serialize its resolved value;
- define the exact trust source for subject and tenant attribution; raw client
  headers never become trusted context by themselves;
- define public event allowlists, redaction rules, payload bounds, delivery
  semantics, backpressure behavior, and sink failure policy;
- define Admin contributor path ownership, dependency injection, conflict
  failure, middleware, and shutdown semantics;
- inventory current Admin and Bundle write payloads, then set the shared body
  limit, rejection status, and bounded JSON error shape without rejecting
  supported payloads below that limit;
- finalize the `LimiterBackend` cancellation, timeout, atomicity, and degraded
  behavior contracts;
- identify every package and symbol that will be designated as a protected
  reusable entry point or Enterprise SPI.

Deliverables:

- focused amendments to `docs/design/enterprise-extension-contract.md`;
- a package/capability ownership matrix for paired-repository review;
- fixture specifications for duplicate registration, unknown modules, missing
  dependencies, secret-reference round trips, cancellation, concurrency, and
  bounded errors, implemented with their owning F1–F5 surfaces.

## 4. Work Package F1 — Reusable Distribution Entry Points

Extract command construction and execution from the three Community
`package main` programs into public packages whose exact paths are frozen in
F0. The thin Community `cmd/.../main.go` files continue to own edition-specific
blank imports and call those packages.

Required behavior:

- preserve all existing flags, Caddy commands, signal handling, startup,
  shutdown, error, and exit-code semantics;
- allow a separately maintained binary to supply an explicit linked-module
  manifest and edition metadata;
- ensure Caddy and standalone consume one runtime capability set;
- let the CLI link only factories and schemas needed for local validation;
- keep server-side apply as the final configuration authority;
- expose no Community `internal/` type in constructors, options, callbacks, or
  results required by an external distribution;
- keep Community binaries free of private imports, license checks, or inactive
  commercial configuration.

Process tests compare old and extracted entry behavior before the old assembly
logic is removed.

Create the separate-module consumer skeleton at this boundary using the package
paths in design section 11.1. Keep old-behavior process evidence before moving
CLI globals or dotenv initialization. F1 is not complete until the external
module constructs and builds all three entries.

### 4.1 F1 implementation evidence

F1 is implemented on the active branch in one consolidated change, including
pre-extraction behavior contracts and accepted review fixes. The separately
rooted `tests/extensionconsumer` module declares the target `v0.7.0` dependency
and is validated against this checkout using an uncommitted temporary modfile
replacement. A consumer contained in the same commit cannot pin that commit
by its own hash; released-tag validation remains a release gate.

Evidence includes:

- all three Community entries and all three external entries build;
- 13 old/new command invocations have identical stdout, stderr and exit codes;
- help, invalid flags, shell/local-dotenv/dotenv precedence and malformed-dotenv
  behavior are covered by process tests;
- Caddy and daemon both start and exit successfully on SIGINT and SIGTERM;
- daemon and CLI instance isolation and mutable option ownership pass race tests;
- external construction does not load dotenv; public signature closure contains
  no Community internal types; direct consumer imports cannot use Community
  main/internal packages or the known private module path;
- the full Community test suite, static checks and independent-consumer gate pass.

Both server mains supply the same explicit metadata set and the CLI supplies a
validation projection. F1 owns value transport and construction; validated
registries, serialized manifest ordering, runtime query wiring and module/schema
validation are now implemented by F2 as recorded in section 5.1. The `extension.Descriptor` metadata shape is introduced
now so F2 can use the same Assembly input rather than replacing an interim type.
Release-tag and paired-private-repository proof remain F6/F7 gates.

## 5. Work Package F2 — Linked Capability Manifest And Configuration

Implement a deterministic, read-only manifest assembled at compile time from
explicit registrations. A manifest entry contains only bounded public metadata:

- stable module ID and module version;
- schema version;
- declared capabilities;
- whether the module participates in server runtime, CLI validation, Admin
  contribution, or an explicitly named domain SPI.

The manifest is not a runtime module loader and contains no entitlement state,
secret, customer metadata, or factory pointer in its serialized form.

Add a bounded configuration envelope and registry that:

- associates namespaced configuration with a stable linked module ID and schema
  version;
- delegates schema/default/dependency validation to the linked factory;
- rejects duplicate registrations, unknown configured modules, and missing
  dependencies explicitly;
- preserves opaque registered configuration through validate/apply/export;
- identifies marked secret-reference fields before generic environment
  expansion, preserves their reference tokens through validate/apply/export,
  and never serializes resolved secret values;
- builds immutable runtime snapshots at mutation time and performs no registry,
  directory, ConfigStore, or license lookup per request;
- lets Community reject a configuration it cannot execute rather than silently
  retaining a disabled security module.

The existing Gateway Bundle remains the declarative workflow. Design section
11.3 fixes the additive envelope, existing-backend store ownership, Community
Admin endpoints, static-source semantics, secret-reference format and mutation
sequence. It must not become an unconstrained `map[string]any` escape hatch for
protocol configuration. Whole-Bundle rollback is outside this slice; extension
snapshot publication must still be atomic and failure-safe.

### 5.1 F2 implementation evidence

F2 is implemented on the active branch. Permanent contracts are recorded in

and the exact candidate symbol list in `pkg/extension/doc.go`.

Evidence includes:

- bounded, deterministic linked registries and sorted manifest projections;
  duplicate/empty registrations, missing/cyclic dependencies and schema errors;
- separate factory registrations with a schema-only CLI projection and frozen

- strict module validation, selected dependencies and envelope count/size/depth
  bounds; local secret syntax checks succeed with the referenced variable unset;
- secret classification before ordinary environment expansion, separate server
  resolution, and reference-preserving Bundle and SQLite round trips;
- existing-backend `extensions` storage, static ownership/conflict checks,
  Caddy JSON/Caddyfile and standalone static-Bundle wiring, and Admin envelope CRUD;
- preparation/persistence failure isolation, lifecycle failure reporting,
  concurrent leases and mutations,
  dependency-only preparation inputs, reverse-order retirement, repeated close,
  panic isolation and shared caller shutdown deadlines;
- extension-first CLI apply with partial-result reporting and effective export;
- independent strict-schema modules using public `contracttest.Registry` and
  `contracttest.Configuration`, with full public-signature/private-import gates;
- actual Caddy and standalone consumer processes proving manifest parity, static

- `make verify-release` passes: all Go tests, independent consumer/build/process

Current preparation rebuilds all configured module handles; preserved domain

body policy remain F4; full protected limiter proof remains F5/F6. Released-tag
and paired-private-repository evidence remain F6/F7 gates.

## 6. Work Package F3 — Shared Attribution And Public Event Boundary

Define a small public attribution value carried through request and event
boundaries:

- authenticated subject identity when established by a trusted resolver or
  existing VirtualKey boundary;
- optional tenant identity from the same trusted source;
- route, Agent, run, VirtualKey, trace, span, and parent correlation when
  available;
- bounded namespaced attributes with an explicit allowlist and size limits.

Absence remains explicit. This package does not authenticate a caller or infer a
tenant from an arbitrary HTTP header.

Define a public event envelope and sink contract that:

- is deliberately separate from `internal/observability/usage`;
- represents attribution, event family, bounded reason/outcome, timestamps, and
  versioned family-specific public data;
- specifies asynchronous delivery, queue bounds, drop/failure counters,
  cancellation, flush, and shutdown semantics;
- excludes prompts, tool arguments, credentials, secrets, arbitrary error text,
  and other content unless a future separately reviewed DTO explicitly permits
  it;
- adapts the existing Community pipeline without creating a parallel event
  authority.

Only event families required by the v0.7 proof slice are designated protected.
Future Audit, Metering, Guardrails, and Policy Decision DTOs are added with
their vertical slices rather than predeclared as empty interfaces.

Use design section 11.4 for the field bounds, two protected event families,
per-sink queues and cancellation/flush/shutdown budgets.

## 7. Work Package F4 — Admin Route Composition

Publish a narrow Admin route-contributor contract that composes with the same
outer Admin protection as Community routes.

It must define:

- stable ownership of method/path pairs and reserved prefixes;
- startup failure for duplicate or conflicting routes;
- a narrow dependency catalog rather than the complete `AgentGateway`;
- the existing CORS, panic recovery, request logging, JSON error, and
  authentication-mount behavior;
- a shared bounded request-body policy, introduced for Community and
  contributed Admin routes before the contributor contract is frozen;
- compatibility tests showing supported existing Admin and Bundle writes below
  the limit still succeed, and both Community and contributed routes reject
  oversized bodies with the specified status and bounded JSON error;
- attribution and public-event hooks for contributed mutations;
- health and shutdown behavior;
- equivalent assembly in Caddy and standalone modes.

The contract does not let modules replace Community routes or bypass the mount
layer's Basic Auth, mTLS, or trusted reverse-proxy authentication.

Use design section 11.5 for namespaces, cross-mux conflicts and the shared
4 MiB/413 policy, including full-body checks before mutation.

## 8. Work Package F5 — Protected LimiterBackend Proof Slice

Use VirtualKey admission as the first real domain SPI that proves the
foundation. Introduce a narrow `LimiterBackend` contract and adapt the existing
in-process token buckets as the Community reference implementation.

The contract covers:

- request context, cancellation, and bounded timeout;
- LLM, MCP, and Agent ingress dimensions already supported by Community;
- atomic admission outcome, retry-after metadata, and bounded diagnostics;
- backend health, initialization, refresh, and shutdown;
- explicit fail-open/fail-closed configuration, with secure defaults for a
  configured hard limit;
- immutable configuration snapshots and no per-request ConfigStore or module
  discovery;
- low-cardinality metrics and public operational events;
- consistent behavior in Caddy and standalone modes.

The Community distribution defaults to its current in-process behavior. A
deterministic external test backend exercises the protected contract; a
production distributed backend is owned by a separately maintained module and
is not required for the Community release.

Use design section 11.6 for selection configuration, the 100 ms default budget,
HTTP 429 versus 503, fail-open/closed and policy-generation retirement semantics.

## 9. Work Package F6 — External Consumer And Paired Repository Proof

Provide reusable public contract suites and an external-module fixture that is
built as a different Go module. It must prove that the consumer can:

- construct all three distributions without importing Community `package main`
  or `internal/` packages;
- register one module, configuration schema, Admin route, event sink, and
  `LimiterBackend` implementation;
- expose the same runtime manifest from Caddy and standalone and the matching
  validation subset from the CLI;
- fail on duplicate/unknown modules and missing dependencies;
- start, admit a bounded request, emit one sanitized event, query the contributed
  Admin route, and shut down cleanly;
- preserve Community protocol, cancellation, streaming, and usage behavior;
- prove the Community binaries contain no imports from the paired private
  module path.

Local cross-repository development may use an uncommitted `go.work` and may run
a non-release compatibility validation against the exact candidate Community
commit. The paired repository's release-gated CI starts from the released v0.7
tag and contains no local replacement, checked-in `go.work`, or unreleased
commit dependency.

## 11. Acceptance Gates

The release candidate must satisfy:

- the repository release verification and smoke gates pass from a clean tree;
- Community command behavior and flags remain covered after extraction;
- a clean external Go module builds Caddy, standalone, and CLI distributions
  using only public Community packages;
- Caddy and standalone report the same runtime capability manifest;
- CLI validation reports the correct schema/factory subset and the server still
  performs final validation;
- duplicate IDs, unknown modules, missing dependencies, configuration schema
  mismatches, and Admin route conflicts fail deterministically;
- marked secret references retain their reference tokens across Bundle
  validate/apply/export even when the referenced environment variable is set,
  and resolved secret values never appear in exported configuration;
- the shared Admin request-body policy preserves supported existing writes and
  returns the specified status and bounded JSON error for oversized Community
  and contributed-route bodies;
- public constructors required by the consumer expose no Community `internal/`
  types;
- every protected attribution field (subject, tenant, route, Agent, run,
  VirtualKey, trace, span, parent, and bounded namespaced attributes) has
  propagation and absence coverage, and attribution never trusts an arbitrary
  caller tenant header;
- public events satisfy redaction, size, queue, drop, flush, and shutdown tests;
- the in-process limiter and external fixture pass the same `LimiterBackend`
  contract suite, including race tests;
- request hot paths perform no ConfigStore, module-directory, manifest, or
  entitlement lookup;
- Community binaries contain no known private import path;
- the paired repository compatibility build passes first against the candidate
  commit and finally against the released tag;
- protected surfaces are explicitly named in package docs and `AGENTS.md`, and
  no repository-wide Enterprise-ready claim is made;
- permanent Community and paired-repository documents describe the same
  ownership, version, and release sequence.

## 12. Recommended Commit Boundaries

1. `docs(extension): freeze v0.7 public foundation contracts`
2. `refactor(distribution): extract entry points and external consumer skeleton`
3. `feat(extension): publish linked capability manifest`
4. `feat(extension): add registered configuration envelope`
5. `feat(extension): publish attribution and event contracts`
6. `feat(admin): add protected route contribution`
7. `feat(limiter): publish backend SPI and reference adapter`
8. `test(extension): add external consumer contract suite`
9. `docs(release): publish v0.7 extension foundation contracts`

Every boundary must keep Community independently buildable and tested. A
public surface is not declared protected before its external-consumer contract
passes.

Required dependency order: F0 decisions → F1 entries/consumer skeleton → F2
manifest/config → F3 attribution/events → F4 Admin/body policy → F5 limiter →
F6 integrated evidence → F7 release closure. Contract fixtures accompany their
own implementation boundary. Community candidate gates use the exact candidate
commit; the paired release-tag gate runs after Community tagging. This avoids
requiring an unpublished tag to pass Community pre-release verification.
