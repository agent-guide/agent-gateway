# v0.7.1 Adoption Readiness Plan

- Status: **Active**
- Target version: **v0.7.1**
- Execution window: **2026-10-20 through 2026-11-17**
- Baseline: Community commit `a74731f7f63886ad4d0840e677285aef1d81f3f2`

## Objective

v0.7.1 makes the capabilities delivered through v0.7.0 straightforward for a
new operator to install, verify, and evaluate. It is an adoption and
distribution release, not a new gateway capability release.

The release must provide downloadable binaries, an official container image,
a deterministic no-provider-key verification path, an optional coding-agent
demonstration, concise first-run documentation, and release gates that exercise
the distributed artifacts rather than only locally built binaries.

The intended first-run outcome is:

1. download the versioned first-run release asset and pull its pinned images
   without cloning the repository;
2. start one self-hosted gateway with persisted local configuration;
3. apply the published copy of the first-run Bundle and retrieve its generated
   VirtualKey;
4. complete a governed Agent turn through the published deterministic HTTP/A2A
   fixture image without purchasing or configuring an LLM provider key;
5. inspect the resulting health, interaction, and metrics data;
6. follow a separate optional path for Codex or OpenCode when the required ACP
   adapter, workspace, and upstream authentication are available.

## Release boundaries

### In scope

- release archives containing `agw`, `agwd`, and `agwctl` for the supported
  Linux and macOS architectures;
- checksums and machine-readable software bill of materials for release
  artifacts;
- a multi-architecture OCI image published under the AgentGuide GitHub
  Container Registry namespace;
- a checksummed first-run release asset containing Compose, Bundle, environment,
  and observability files, plus a separately versioned development fixture image;
- a Docker Compose first-run environment and optional observability profile;
- a deterministic, provider-credential-free HTTP/A2A smoke scenario;
- a separate coding-agent scenario for the existing Codex and OpenCode ACP
  runtimes;
- a shorter repository landing path, synchronized English and Chinese product
  pages, and task-oriented installation and upgrade documentation;
- contributor onboarding and repository metadata needed before public launch;
- CI and release gates for archives, images, examples, links, and version
  metadata.

### Out of scope

- new LLM, MCP, ACP, A2A, or Agent protocol behavior;
- a new Agent runtime type or provider type;
- a Web administration console;
- enterprise IAM, SSO, organization or role models;
- distributed rate limiting, high availability, cost budgets, durable audit,
  memory, scheduling, or durable workflows;
- changes to Bundle schemas, Admin API paths, route semantics, or persisted
  record formats;
- compatibility aliases or migration shims for old names or shapes;
- shipping `agw-auth` inside the Community image. OAuth refresh continues to
  require the separately installed external executable and documented command
  configuration.

Items in the second list require their own design and version decision. They do
not block v0.7.1 adoption readiness.

## Compatibility requirements

v0.7.1 must preserve every surface designated at v0.7.0 in
[the Enterprise Extension Contract](../design/enterprise-extension-contract.md)
and [the v0.7.0 release notes](../releases/v0.7.0.md). Distribution packaging
must consume those entries without moving command construction, dotenv,
signals, or process exit into the three `cmd` packages.

The release must not change configuration or request behavior merely to make a
demonstration shorter. Examples use the current Bundle, route, VirtualKey, ACP,
HTTP Agent, MCP, and observability contracts. Any defect found while building
the examples is fixed at its owning layer with regression coverage; a behavior
change that expands the scope above is re-homed to a later version.

The runtime and validation manifest projections remain distinct. `agw manifest`
and `agwd manifest` must equal `CommunityRuntime().Manifest()`, while
`agwctl manifest` must equal `CommunityValidation().Manifest()`. Each projection
must report `0.7.1` in `edition.version` and in every included Community module
version. Archive names, image labels, Git tags, checksums, and release notes must
agree on that version. The upstream `agw version` command reports the Caddy
version and is not Agent Gateway release identity.

## Baseline

The baseline already provides:

- three explicit binaries: `agw`, `agwd`, and `agwctl`;
- Caddy and standalone runtime assemblies;
- idempotent Bundle validation, apply, and export;
- LLM, MCP, builtin Agent, ACP, and HTTP/A2A data paths;
- persisted usage events, Prometheus exposition, and optional OTLP export;
- process smoke coverage for both server modes and HTTP Agent Path A and Path B;
- source release gates and published-dependency acceptance for the protected
  v0.7.0 surfaces;
- separate quick starts for LLM, MCP, ACP, and HTTP Agent operation.

The baseline does not provide:

- checked-in container or Compose definitions;
- a tag-triggered artifact publishing workflow;
- downloadable executable archives in the v0.7.0 GitHub release;
- one provider-credential-free first-run path that validates a published
  distribution;
- provisioned dashboards for the existing Prometheus and OTLP surfaces;
- artifact-level smoke tests or image security checks;
- a concise README path from product purpose to first successful request;
- repository community files or automated documentation-link checks.

## Work package 1 Release artifacts and version identity

### Deliverables

- Add a tag-triggered release workflow that first runs the existing release
  gates and then builds supported archives from the tagged commit.
- Publish archives for:
  - Linux amd64;
  - Linux arm64;
  - macOS amd64;
  - macOS arm64.
- Package all three binaries, `LICENSE`, and a short installation/readme file in
  each platform archive.
- Publish a platform-independent
  `agent-gateway-first-run-v0.7.1.tar.gz` release asset containing the Compose
  project, its Bundle, a placeholder-only environment template, setup and smoke
  commands, and the optional observability provisioning files. The archive must
  not contain binaries duplicated from the platform archives or any credential.
- Publish `SHA256SUMS` covering every archive, including the first-run asset, and
  an SBOM generated from the exact tag contents.
- Record the source commit, Go version, target tuple, and version in release
  metadata.
- Fail publication when the tag, archive or image metadata, or the version
  fields in either Community manifest projection disagree.
- Keep signing or provenance generation in the workflow when it can use GitHub
  workload identity without a long-lived repository secret; do not make an
  unverifiable signing claim.

### Verification

- Extract each archive into a fresh temporary directory and run `manifest` on
  all three binaries. Assert that `agw` and `agwd` match the runtime projection,
  that `agwctl` matches the validation projection, and that each projection has
  the expected edition and included-module versions.
- Run the existing process smoke against the Linux release binaries through
  `AGW_RELEASE_BIN_DIR`.
- Build macOS archives on macOS runners and execute their local manifest checks;
  do not treat unexecuted cross-compiled files as release evidence.
- Reject archives that contain absolute paths, source-tree build output, local
  configuration, database files, or secrets.
- Extract the first-run asset outside a repository checkout, verify its checksum,
  and confirm that every local path referenced by Compose is present in that
  asset.

## Work package 2 Official container distribution

### Deliverables

- Add one multi-stage Dockerfile that produces a minimal runtime image
  containing `agw`, `agwd`, and `agwctl`.
- Run as a fixed non-root user and document the writable data directory and
  mount contract.
- Use `agwd` as the default command. Document how to select `agw` for Caddy
  configurations and `agwctl` for management operations.
- Publish the gateway image as
  `ghcr.io/agent-guide/agent-gateway:v0.7.1` with a commit-digest tag. Move
  `latest` only after the versioned image passes post-publish smoke verification.
- Publish the deterministic A2A development fixture separately as a
  multi-architecture image at
  `ghcr.io/agent-guide/agent-gateway-a2a-fixture:v0.7.1` with a commit-digest tag.
  Record its immutable digest in the first-run Compose file; do not add the
  fixture to the production gateway image.
- Make both GHCR packages public before any GitHub Release is published. New
  GHCR packages default to private even when a workflow links them to a public
  repository, so the first tag run may require an organization owner to change
  both package visibility settings and rerun the failed release jobs.
- Apply OCI labels for source repository, revision, version, license, and
  documentation URL.
- Document that the image does not embed provider credentials or `agw-auth`.
- Call the existing public `GET /admin/health` route through the container's
  loopback address. The standalone server intentionally exempts this probe from
  Admin Basic Auth; do not change its authentication semantics or add another
  health route for Docker.

### Verification

- Build and run linux/amd64 and linux/arm64 images in CI.
- Start the image with a read-only root filesystem plus only the documented
  writable mount and temporary filesystem exceptions.
- Confirm the process runs as non-root, persists SQLite state across container
  replacement, handles termination, and reports `0.7.1` through the runtime
  manifest projection.
- Scan the final image for known operating-system and Go dependency
  vulnerabilities. Record accepted findings in the release notes with scope and
  remediation status.
- Pull both immutable image digests from a fresh job that performs no registry
  login. Treat this credential-free pull as a prerequisite of first-run asset
  execution and GitHub Release publication, not as a post-publication warning.

## Work package 3 First run and coding agent demonstrations

### Provider credential free first run

Add a Compose environment that starts:

- the published Agent Gateway image;
- the separately published image of the existing deterministic development A2A
  fixture;
- a persistent gateway data volume;
- an initialization step that validates and applies the copy of the Bundle
  shipped in the first-run release asset.

The provider-credential-free Compose topology is part of the acceptance
contract:

- run `agwd` with its data listener on `0.0.0.0:8080`, publish that listener only
  on host `127.0.0.1:8080`, keep the Admin listener on
  `127.0.0.1:8019` inside the gateway network namespace, and do not publish the
  Admin port;
- run the A2A fixture and initialization services with
  `network_mode: service:gateway`. The fixture continues to listen on
  `127.0.0.1:8090`, so its Card and selected JSON-RPC interface remain loopback
  HTTP as required by the current runtime contract. Do not replace this with an
  insecure bridge-network HTTP hostname; a future topology that does not share
  the namespace must terminate real HTTPS;
- probe the existing public `GET /admin/health` on
  `http://127.0.0.1:8019` from the gateway namespace. The initialization service
  waits for both that probe and the fixture's loopback health endpoint before
  applying configuration;
- enable standalone Admin Basic Auth even though the Admin listener remains on
  loopback. The setup command accepts a user-supplied development password, uses
  `agw hash-password` from the pinned gateway image, and creates an untracked
  local environment file. Set `AGW_ADMIN_BASIC_AUTH` for `agwctl` to the complete
  `admin:<plaintext-password>` value and `AGW_ADMIN_BASIC_AUTH_HASH` for `agwd` to
  the complete `admin:<bcrypt-output>` value. Preserve the bcrypt output's `$`
  characters with Compose-compatible quoting or escaping. The published template
  contains placeholders only, and the guide marks the credential as
  non-production;
- use `http://127.0.0.1:8080` as the canonical documented client URL and set the
  native A2A route's `match_policy.host` to `127.0.0.1`. Tests must use that
  actual request Host rather than overriding route matching implicitly.

The documented flow must retrieve a generated VirtualKey, call the common
Agent `/turn` path, call the governed native A2A JSON-RPC path, and query the
matching interaction or metrics surface. The fixture remains clearly labeled
as deterministic development infrastructure rather than a production Agent
SDK.

After the release asset and images are downloaded, the base Compose flow must
not require a provider account, npm package, local Go toolchain, externally
installed database, or external cloud service at runtime.

### Optional coding agent demonstration

Add a second profile or task-oriented guide for the existing Codex and OpenCode
ACP runtimes. It must state the external adapter, workspace, authentication, and
permission-mode prerequisites before the first command. The scenario exercises:

- Agent and AgentRoute application through `agwctl`;
- VirtualKey-protected streaming `/turn` ingress;
- runtime inspection and exact-run cancellation;
- session listing and transcript replay when the selected adapter advertises
  those capabilities;
- interactive permission decisions in a configuration that supports them.

The guide must not imply that Claude Code is an ACP backend. Claude Code remains
a gateway consumer through the `cc` Anthropic Messages profile.

### Verification

- CI extracts the built first-run asset outside the repository checkout, starts
  the provider-credential-free Compose path, waits on the two declared health
  endpoints rather than fixed sleeps, exercises both Agent ingress paths using
  the documented Host, and tears down volumes and processes on every exit.
- The source Bundle and its published copy are byte-identical, pass local
  validation, and remain idempotent on a second apply.
- The optional ACP guide is checked for command and configuration syntax; its
  external login cannot be treated as unattended CI evidence.

## Work package 4 Observable evaluation environment

### Deliverables

- Add an optional Compose observability profile using the gateway's current
  Prometheus exposition and OTLP export contracts.
- Provision data sources and the smallest useful views for request volume,
  errors, latency, token counts, limiter outcomes, event-pipeline health, and
  Agent interactions. Prometheus panels may query only
  `agentgateway_usage_requests_total`, `agentgateway_usage_failures_total`,
  `agentgateway_usage_tokens_total`, `agentgateway_usage_dropped_events_total`,
  `agentgateway_usage_write_failures_total`, and
  `agentgateway_limiter_admissions_total`.
- Show latency from OTLP span duration or the Admin summary APIs'
  `avg_latency_ms`; do not invent or document a Prometheus latency series.
- Treat the successful provider-credential-free A2A run as evidence only for an
  interaction and an increase in
  `agentgateway_usage_requests_total{route_kind="agent",runtime_type="http"}`. A
  successful turn does not create a failure-series sample, token usage, or
  model/tool child spans. Check `agentgateway_usage_failures_total` only in a
  separate controlled scenario that produces a failed HTTP Agent turn. Validate
  token panels with an explicitly optional LLM scenario that returns usage, and
  validate model/tool child views only with a scenario that actually invokes
  those components.
- Provide a trace view that demonstrates the interaction parent span and its
  Agent, model, and tool children when the selected scenario produces them.
- Keep telemetry components outside the default first-run critical path.
- State retention, authentication, and non-production defaults explicitly.

### Verification

- Provisioned dashboards load without manual edits.
- Metrics queries refer only to names emitted by the checked-in gateway.
- The base demo asserts that at least one successful A2A interaction is
  observable and that its `agent`/`http` request counter increases. A failure
  counter assertion requires a separate failed-turn scenario. Any optional
  usage-producing scenario separately asserts its token or component telemetry;
  screenshots alone are not acceptance evidence.

## Work package 5 Documentation and website conversion path

### Repository documentation

- Reduce the README opening to product purpose, concrete differentiation, one
  architecture view, the shortest supported installation path, and links to
  task-oriented documentation.
- Move the legacy `cliauth_token` to `oauth_token` SQL procedure to a dedicated
  upgrade guide. Label it as applying to stores that have not completed the
  external CLI-auth cutover already documented since v0.5.0; retain a short,
  visible warning and link where operators of those stores will see it.
- Add a separate v0.7.0 section to the upgrade guide covering the complete
  compatibility and migration section of the v0.7.0 release note:
  - Admin requests validate the complete received body, reject bodies over 4 MiB
    and compressed bodies, apply the Bundle boundary per resource rather than to
    the total local YAML file, and return bounded JSON 500 responses without
    panic diagnostics;
  - extension configuration moved out of Caddyfile, Caddy JSON, and standalone
    static Bundles; startup and reload no longer import extension envelopes, and
    extension consumers must account for the removed static-bootstrap APIs;
  - secret fields require declared `{"$secret_ref":"env:NAME"}` references and
    preserve those tokens through persistence and export; and
  - limiter selection schema 1 defines linked backends, the `timeout_ms` and
    `failure_mode` defaults and ranges, 429 exhaustion and bounded 503 failure
    behavior, fail-open exclusions, non-retryable consumes, and the generation
    reset, fencing, and state-preservation rules.
- Add one canonical first-run guide for published archives and the container.
  Keep the protocol-specific quick starts for deeper LLM, MCP, ACP, and HTTP
  Agent setup.
- Add a release-installation guide covering checksums, version verification,
  data mounts, Admin authentication, external credential refresh, upgrade, and
  rollback preparation.
- Add an evaluated-capabilities table that distinguishes implemented behavior,
  optional external dependencies, and roadmap items.
- Check all shell examples for the executable and configuration shape they
  claim to use.

- Show one concrete governed Agent request and one observable result before the

- Keep counts, runtime types, supported protocols, and roadmap labels aligned

- Apply every content change to both `website/` and `website/zh/` according to

### Community entry points

- Configure the GitHub repository homepage and relevant topics.

## Work package 6 Release verification and publication

### Required gates before tagging

Run the existing source and compatibility gates on the exact clean candidate:

```sh
make verify-release
make smoke-release
make test-extension-consumer-candidate COMMUNITY_COMMIT=<full-commit>
```

The paired consumer must pass against the same full commit. In addition:

- build and smoke all publishable archives;
- build and smoke both target architectures of the gateway and A2A fixture
  images;
- package the first-run release asset and execute it from an empty directory
  outside the repository checkout;
- validate every checked-in Bundle used by installation documentation;
- check internal documentation links and bilingual page parity;
- verify that no example, layer, log, artifact, or SBOM contains a test secret;
- confirm that the protected v0.7.0 symbol and contract suites pass unchanged;
- review the generated v0.7.1 release note against the actual artifact manifest.

### Publication sequence

1. Freeze the candidate and record its full commit.
2. Pass Community and paired-consumer candidate gates.
3. Tag `v0.7.1` from that exact commit.
4. Publish the versioned gateway and fixture images and record their immutable
   digests. On the first publication, make both new GHCR packages public and
   rerun the failed jobs if the credential-free image gate reports the default
   private visibility.
5. Generate the first-run archive with those digests, then publish it with the
   platform archives, checksums, and SBOM.
6. Download the first-run archive from the public release, verify its checksum,
   resolve the two images by their recorded digests, and run the artifact and
   image smoke tests without a repository checkout.
7. Move `latest` only after versioned-image verification.
8. After the tag resolves from the public Go module proxy, update the checked-in
   separate consumer and the independently maintained paired consumer to
   `v0.7.1`, including their module checksums. Run both released-dependency gates
   with fresh caches, `GOWORK=off`, and no replacement. Re-running their existing
   `v0.7.0` pins does not satisfy v0.7.1 acceptance.
9. Publish the hosted release description from `docs/releases/v0.7.1.md`.
10. Deploy the synchronized English and Chinese website and verify public links.

## Release acceptance

v0.7.1 is complete only when all of the following are true:

- a new user can install a supported archive without a Go toolchain;
- a new user can pull the versioned official images and verify their recorded
  immutable digests;
- a new user can download the checksummed first-run asset and run its Compose
  project without cloning the repository or resolving repository-relative files;
- the provider-credential-free Compose path reaches a successful governed Agent
  turn using only documented commands;
- the same flow proves persistence, VirtualKey enforcement, and at least one
  interaction or metrics record;
- `agw` and `agwd` report the v0.7.1 runtime manifest projection, while `agwctl`
  reports the v0.7.1 validation projection, and each equals its corresponding
  Community assembly manifest;
- archives and images pass post-publication smoke checks;
- the optional ACP guide states and validates every prerequisite it controls;
- English and Chinese website claims match the released capability set;
- the compatibility surfaces first designated at v0.7.0 pass published-tag
  consumer acceptance against v0.7.1;
- permanent guides describe installation and operation, and
  `docs/releases/v0.7.1.md` records the shipped result and known limits.

## Risks and controls

| Risk | Control |
| --- | --- |
| Packaging exposes an untested platform | Publish only target tuples executed on native or emulated CI runners with a recorded smoke result. |
| Container examples expose or bypass Admin authentication | Keep Admin on loopback inside the shared gateway namespace, do not publish its port, enable explicit development-only Basic Auth for initialization, and publish only placeholder credentials. |
| The coding-agent demo appears credential-free | Keep it separate from the deterministic A2A first run and list adapter and authentication prerequisites first. |
| README simplification removes operational warnings | Move detail to an upgrade or operations guide and preserve visible links for existing operators. |
| Marketing language outruns the release | Generate capability tables from the tagged scope and review both website languages against the release note. |
| Packaging work changes protected command behavior | Exercise the public distribution contract suites and keep all process lifecycle rules in their current owners. |
| A new GHCR package remains private | Require anonymous digest pulls before publishing the GitHub Release; on the first run, an organization owner changes both package visibility settings to Public and reruns the failed jobs. |
| `latest` points to an unverified image | Publish the versioned image and record its digest first; promote `latest` only after public-image smoke verification. |

## Deletion condition

Delete this plan after v0.7.1 is published, public artifacts pass their
post-publication checks, the permanent guides and release notes describe the
landed behavior, and any unfinished item has been explicitly re-homed to another
active plan or durable proposed design. Git history remains the record of this
execution plan.
