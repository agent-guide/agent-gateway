# v0.6.1 Stabilization Plan

## 0. Plan Contract

This plan targets the `v0.6.1` patch line. Its objective is to prove and
package the behavior shipped in `v0.6.0`, not to add another runtime,
protocol, persistence model, or policy subsystem.

The baseline was verified at annotated tag `v0.6.0`, commit
`339b15afda5ea7e611de255091bdc6884d52c0e1`. When this plan and the code
disagree, the code wins and this plan must be corrected before implementation
continues.

Implementation rules:

- each work package lands as a reviewable commit with its own verification;
- runtime behavior changes are limited to defects demonstrated by a regression
  test;
- no compatibility alias or legacy route shape is introduced;
- permanent behavior belongs in guides, reference, architecture, and release
  notes, not in this plan;
- `v0.6.1` is not tagged until every release gate in §7 passes on the final
  commit.

## 1. Scope

The patch release delivers four outcomes:

1. one reproducible release-verification entry point shared by developers and
   CI;
2. a self-contained local A2A Protocol 1.0 example for the HTTP Agent quick
   start;
3. process-level smoke coverage for the shipped binaries and both HTTP Agent
   ingress paths;
4. explicit fresh-database and pre-v0.6 SQLite schema-upgrade coverage.

Any newly discovered correctness or security defect may be fixed in this line
only with a focused regression test and release-note entry.

## 2. Non-Goals

`v0.6.1` does not add:

- A2A v0.3, REST, gRPC, push webhooks, or extended-card support;
- durable or cross-replica HTTP Agent task bindings;
- new Guardrails, Memory, Pipeline, Workflow, or callback-identity behavior;
- reverse translation of ACP or builtin Agents to native A2A;
- a second release mechanism or generated compatibility aliases.

## 3. Work Package S1 — Release Verification Parity

Create one repository-owned verification entry point, exposed through the
Makefile or a small checked-in script, that normalizes and performs the release
checks currently split between `docs/releases/v0.6.0.md` and CI:

```text
tracked-Go-file formatting check with gofmt -l (non-mutating)
go mod verify
go test ./...
race test, excluding only pkg/llm/provider/anthropic
go vet ./...
build agw, agwd, and agwctl
```

Requirements:

- CI and the release guide invoke the same entry point or the same documented
  command sequence; they must not maintain divergent package exclusions.
- The shared entry point owns the exact formatting file set: tracked Go files
  excluding `third_party/**`. CI and release documentation invoke that entry
  point instead of reproducing the file-selection or exclusion rules.
- Formatting verification reports a dirty file without rewriting the tree.
- The Anthropic race exclusion retains an adjacent explanation and is removed
  when the pinned upstream dependency no longer requires it.
- Build output names remain `agw`, `agwd`, and `agwctl`.
- A successful verification leaves the Git worktree clean.

Verification:

- run the entry point locally from a clean checkout;
- run the GitHub Actions workflow on Linux;
- deliberately format-drift a tracked Go fixture, prove the formatting gate
  fails without rewriting that file, and restore the fixture after the check.

## 4. Work Package S2 — Self-Contained A2A Example

Add a minimal example A2A Protocol 1.0 JSON-RPC service under `examples/` that
can be started with repository tooling and no vendor account. It is a protocol
fixture for onboarding and smoke tests, not a production Agent SDK.

Required behavior:

- serve an Agent Card with a same-origin `JSONRPC` interface and protocol
  version `1.0`;
- accept `A2A-Version: 1.0`;
- implement deterministic `SendMessage` and `SendStreamingMessage` responses:
  the synchronous method returns either an agent-authored `Message` or a
  completed `Task`, and the streaming method ends with a terminal status update
  before closing;
- return a stable A2A `contextId` that the gateway can bind to its
  caller-visible `session_id`, so the common `/turn` continuation can be
  demonstrated without exposing the remote identifier as the client contract;
- expose a deterministic health/readiness signal for the smoke harness;
- bind loopback by default and print no credentials or request bodies;
- shut down cleanly when the test harness exits.

The example need not implement the full six-method native-ingress allowlist.
Unsupported methods return a protocol-correct JSON-RPC error and are documented
as example limitations.

Documentation changes:

- update the root HTTP Agent quick start and
  `docs/getting-started/quickstart-http-agent.md` with an optional local-example
  path;
- keep the existing bring-your-own A2A service path;
- state clearly that the fixture is for development and verification only.

Verification:

- Card parsing and interface selection use the real `pkg/a2a/card` code;
- JSON and SSE responses use the real Path B client and Path A proxy tests;
- the example starts on an ephemeral or explicitly supplied loopback port.

## 5. Work Package S3 — Process-Level Release Smoke Test

Add a deterministic smoke harness that builds and exercises the binaries as
separate processes. It must use temporary directories, loopback listeners, and
bounded startup/exit deadlines, and must clean up child processes on success,
failure, or interruption.

The primary scenario is:

1. start the example A2A service;
2. start `agw` with a temporary SQLite config store and the Agent dispatcher
   enabled;
3. apply one HTTP Agent, one `protocol=agent` route, one `protocol=a2a` route,
   and one VirtualKey through `agwctl`;
4. verify readiness through the Admin API or `agwctl`;
5. send one common `/turn` request and observe a terminal common Agent SSE
   event;
6. fetch the rewritten public Agent Card;
7. send one native `SendMessage` request and one native
   `SendStreamingMessage` request;
8. verify the ingress VirtualKey is absent southbound;
9. poll the unified interaction query by stable trace and route dimensions with
   a bounded deadline until the matching A2A usage event is persisted;
10. terminate all processes and verify clean exit.

The standalone daemon receives a narrower smoke scenario: start `agwd` from a
temporary static configuration, prove its Admin/readiness surface is usable,
and stop it cleanly. The test is not required to duplicate every Caddy-path
assertion.

Requirements:

- no fixed developer-machine paths or globally reserved ports;
- no outbound network dependency;
- no fixed sleeps used as readiness or persistence guarantees; use bounded
  polling for process readiness and asynchronous usage-event persistence;
- failure output includes the relevant child-process logs without exposing
  secrets;
- the harness is runnable locally and in GitHub Actions.

## 6. Work Package S4 — SQLite Upgrade Coverage

Pin both database initialization paths in automated tests:

### S4.1 Fresh database

- initialize an empty SQLite database through the production schema path;
- assert all five usage tables and required indexes exist;
- write and query an A2A interaction through the production sink/query APIs.

### S4.2 Pre-v0.6 database

- construct a minimal pre-v0.6 schema fixture without
  `a2a_usage_events`;
- retain representative existing LLM, MCP, ACP, and builtin rows;
- start the production migration path;
- assert existing rows are unchanged and the A2A table/indexes are added;
- write an A2A event and verify the SQLite summary, recent-event, and unified
  interaction queries can read it;
- independently pass a representative A2A interaction event through the OTLP
  adapter and verify the resulting span projection.

The fixture should be expressed as reviewable schema/test setup rather than a
committed opaque database binary. The test must not depend on running an old
gateway executable.

## 7. Release Gates

The final `v0.6.1` candidate must satisfy all of the following:

- the shared release-verification entry point passes;
- GitHub CI is green on the exact candidate commit;
- the process smoke test passes on Linux from a clean checkout;
- fresh and pre-v0.6 SQLite tests pass;
- the HTTP Agent quick start succeeds against the local example exactly as
  written;
- `git diff --check` passes and the worktree is clean;
- no new external network dependency is required by tests;
- `docs/releases/v0.6.1.md` records fixes, verification, and any remaining
  limitations;
- website changes, if any, are applied to both English and Chinese pages.

## 8. Documentation Impact

Expected permanent-document changes:

- `README.md` — optional local HTTP Agent example path;
- `docs/getting-started/quickstart-http-agent.md` — self-contained walkthrough;
- `docs/development/README.md` — release verification and smoke commands;
- `.github/workflows/ci.yml` — shared verification/smoke invocation;
- `docs/releases/v0.6.1.md` and `docs/releases/README.md` — delivered outcome.

Architecture and design documents change only if a verified runtime defect
changes a durable contract. Test mechanics and completed checklist state do not
move into those documents.

## 9. Deletion Condition

Delete this plan when `v0.6.1` is tagged and all work packages are either
delivered or explicitly removed from the release scope, permanent docs describe
the resulting behavior, `docs/releases/v0.6.1.md` records the outcome, and the
plan's entries have been removed from both `docs/README.md` and
`docs/plans/README.md`. Git history remains the implementation archive.
