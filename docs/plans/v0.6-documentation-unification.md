# v0.6 Documentation Unification Plan

## Objective

Prepare the repository documentation for `v0.6.0` under one ownership model:

- Design explains why the system has its shape and which rules must hold.
- Architecture explains how the checked-in system currently runs.
- Plans explain work actively being prepared or executed.
- Release notes explain what a published version delivered.

The work also closes stale capability claims introduced while HTTP Agent
Runtime Path B and Path A were landing.

## Baseline

- branch: `feature/http-agent-runtime`
- starting commit: `971c0f0`
- previous release: `v0.5.1`
- target release: `v0.6.0`

Code is the source of truth when an existing document disagrees with the
implementation. Completed plans are deleted after their durable content is
re-homed; Git history is the archive.

## Work Packages

### D1: Current architecture

- describe HTTP Agent Path A and Path B in the current architecture;
- align Agent, MCP, config-store, and observability descriptions with the
  checked-in runtime;
- keep proposed pipelines, memory, and workflows out of current flows.

Acceptance: architecture pages contain no unmarked proposed behavior and cover
all implemented runtime types and ingress protocols.

### D2: Durable implemented designs

- remove completed phase tables, commit histories, migration checklists, and
  file-by-file implementation tasks;
- retain decisions, contracts, invariants, limitations, and rejected
  alternatives;
- use current-tense behavior and one document-level capability status.

Acceptance: implemented designs remain sufficient to review behavior without
acting as historical project trackers.

### D3: Proposed designs

- mark unshipped designs `Proposed`;
- remove unscheduled implementation sequences and completion checklists;
- retain prerequisites, intended contracts, tradeoffs, and non-goals.

Acceptance: no proposed document can be mistaken for a shipped capability or
an active delivery commitment.

### D4: Plan lifecycle cleanup

- re-home durable content from completed plans;
- delete the v0.4 completion, observability implementation, and unified Agent
  runtime plans once current documentation covers their results;
- keep only active plans in the plan index.

Acceptance: every listed plan represents unfinished, intentionally active
work.

### D5: Operator documentation

- add an HTTP Agent quick start, task guide, and A2A ingress reference;
- align route, Admin API, Caddyfile, CLI, bundle, credential, and runtime-mode
  references;
- update root documentation and both website languages where claims change.

Acceptance: an operator can configure and verify Path A and Path B without
reading a design document.

### D6: Release record

- create `docs/releases/v0.6.0.md` from `v0.5.1..HEAD`;
- record user-visible additions, changes, fixes, migration concerns, known
  limitations, and verification.

Acceptance: the versioned file can be used directly as the hosted release
description.

### D7: Consistency verification and closure

- validate relative links and index coverage;
- search for stale version, roadmap, runtime, and protocol claims;
- verify documented configuration and command examples against code;
- run formatting, module verification, tests, vet, and binary builds;
- delete this plan after all other acceptance gates pass.

## Commit Strategy

Each work package is committed independently. Large design cleanup may use
multiple subsystem-scoped commits when that makes review safer. Moves and link
updates occur in the same commit.

## Deletion Condition

Delete this file when D1-D7 are complete, permanent documents describe the
result, `docs/releases/v0.6.0.md` exists, and the final verification gates pass.
