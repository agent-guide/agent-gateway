为什么选 AgentGuide

一个控制平面，而不是又一个 Agent 框架。

LangGraph、AutoGen、CrewAI 回答的是"agent 该怎么思考？" AgentGuide 回答的是另一个问题："组织该怎么运营 agent？" —— 谁可以调用它们、它们能触碰什么，以及每个受治理请求留下了哪些证据。 一个负责造 Agent，另一个负责运营它们周围的共享 Runtime 路径。

本质区别

框架编排推理，AgentGuide 治理共享 Runtime 路径。

框架的工作流活在单个 agent 进程内部：规划、调用工具、反思、重试。 AgentGuide 的控制围绕 Agent 展开：身份、路由、Runtime 生命周期、会话、策略 与归因。持久任务、调度和跨 Agent Workflow 属于外部上层，相关集成仍在路线图中。

AgentGuide 刻意不替代你的框架 —— 它把兼容的框架 Agent 接入共享路由。 Builtin 运行时本身就内嵌了一个 Agent 框架来支撑拓扑； 而网关的职责始终不变：定义、生命周期、治理、资源与观测。

  • Builtin 运行时 内嵌框架之上的声明式 agent —— 两层可以共存的活证据。
  • ACP 运行时 Codex、OpenCode 等讲协议的 agent，以黑盒方式托管。
  • HTTP 运行时 LangGraph、ADK 或自研服务可通过翻译后的 A2A Protocol 1.0 轮次或原生受治理 A2A 代理入口执行。
  • 协议边界 ACP agent 作为受管黑盒运行；外部 HTTP agent 保留自己的实现栈。

选择合适的工具

什么时候适合 AgentGuide，什么时候不适合。

当 Coding Agent Runtime 控制与 LLM/MCP 治理需要共用一个自托管边界时， AgentGuide 最有价值；但它不是所有 AI Gateway 需求的默认答案。

适合

在这些情况下选择 AgentGuide

  • 你需要自托管 Codex、OpenCode、Builtin 或远程 A2A Agent 的 Runtime 管理。
  • 同一个控制点需要治理 Agent Turn、受支持的 LLM API 与 MCP 工具。
  • 私有部署、VirtualKey、权限与运行证据比托管 UI 更重要。
其他路径可能更合适

在这些情况下选择其他工具或等待

  • 首要需求是最广的 LLM Provider 目录、费用预算和管理 UI：评估 LiteLLM。
  • 已经标准化使用 Kong 或 Konnect，并希望用其 AI Policy 治理 LLM、MCP 与 A2A 流量：评估 Kong AI Gateway。
  • 主要需要托管式 LLM 可观测、Guardrail、治理与 Prompt 管理套件：评估 PRISMA AIRS AI Gateway（原 Portkey）。
  • 现在就需要内置企业 SSO/RBAC、HA 集群、分布式限流、预算执行或合规审计账本：这些不是当前 Community 能力。

未来的方向

从受治理的 Agent，到更大的能力网络。

团队未来可能通过外部 Workflow 层运营许多专业 Agent。以下是目标抽象 —— 它们是路线图设想，不是当前网关已经具备的能力。

vision · artifact bus

流转工作成果，而不是 prompt 链

agent 之间交换的是有版本、可审计的工件 —— PRD、架构、patch、评审 —— 而不是裸文本。每个工件都有生产者、消费者、版本与审批状态， 连成一张血缘图，一次查询就能回答"为什么失败了？"

vision · 能力组合

要结果，不点名 Agent

声明你需要的能力 —— "审这份合同"、"发布这个服务" —— 由平台决定哪些 agent 组合起来交付它，靠它们消费与产出的工件类型自动连线。

vision · agent teams

调用一支团队，而不是一个 Agent

具名团队 —— PM、架构师、编码、评审 —— 成为一等对象， 带角色路由与 supervisor 策略。今天已交付的进程内 supervisor 与 plan-execute 拓扑是第一步。

vision · 共享记忆

整个舰队的黑板

workspace 级的共享记忆，供协作中的 agent 读写 —— 比任何单个会话都长寿的上下文，和其他资源一样受治理。

从价值所在开始

控制平面从第一个 Agent 就开始回本。

不需要先有一支舰队：把一个 agent 的流量接进 AgentGuide， 第一天你就拿到归因、密钥与审批。编排层会建在一个你已经信任的地基上。
